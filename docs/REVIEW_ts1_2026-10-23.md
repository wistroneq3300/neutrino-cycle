## 一、白話總結

這一個 branch 主要在做三件事：把 dmesg 的錯誤「一網打盡」成一個 bundle（WP4）、讓 journal 可以在多個位置被找到並新增 `--journal`（WP5）、以及把報告上「bundle」這個內部名稱改成操作員看得懂的 `fail/error` 並保留裝置位址（WP6）。

整體而言，程式結構清楚、測試覆蓋紮實，官方要求的 WP4/WP5/WP6 幾乎都已經落地。我這次獨立審查後**另外找到 2 個真正會出錯的 bug 並已修好**：(1) Redfish 的 EventLog 與 SEL 共用同一組 delta id 會造成誤判 NEW；(2) 舊格式的 campaign（`pci` 是字串對照表）在離線 rebuild 報告時會直接崩潰，導致整份報告生不出來。兩個 bug 都補了回歸測試，全套測試維持全綠。

其餘 ChatGPT 提出的 findings 大多屬於「現行設計已經處理好」或「設計取捨而非 bug」，詳見下面的逐一驗證。

## 二、ChatGPT Findings 逐一獨立驗證

下面每個 finding 我都實際去看程式、跑測試或合成輸入驗證，不直接採信。

### A. `stop_cycle.sh --force <Run_ID>` 是否會跨 Campaign 誤停？

**結論：已修好、目前安全。**

| 檢查點 | 現況 | 佐證 |
|---|---|---|
| 跨 Campaign 誤停 | 已用 `run_id` 限定 | `lock_holders` / `terminate_holders` / `report_holders` 都帶 `"${1:-}"`；`--force <id>` 只清該 run 的 holder |
| PID reuse 保護 | 有 | `/proc/<pid>` 檢查 uid + cmdline 必須含 `neutrino_cycle.py` |
| 停不掉的處理 | 有 | SIGTERM → 等 10 秒 → SIGKILL，最後再檢查殘留 lock |
| 無 Run ID 的 `--force` | 刻意全帳號 | 這是文件定義的語意（bare `--force`），不是 bug |

白話：以前 `--force` 可能把隔壁正在跑的 campaign 一起砍掉，現在指定 Run ID 就只砍那一個；沒有指定時仍是「砍本帳號所有 holder」，這是原始設計。

### B. APEI-only 時 `_dmesg_package_html(bundle=None)` 會不會 AttributeError？

**結論：安全，已用防護 + 測試固定。**

- `_dmesg_severity` 內有 `if not item: continue`，空 slot 不會被解參考。
- `_dmesg_package_html` 用 `packages = [i for i in [bundle, *apei] if i]`，`bundle=None` 安全。
- 測試 `test_dmesg_package_html_survives_every_capture_shape` 覆蓋 `[] / APEI-only / BUNDLE-only / APEI+BUNDLE` 四種形狀。

### C. dmesg fingerprint / dedup 用 `(boot_id, raw)` 是否會把不同 BDF 合成一個、漏抓第二張卡？

**結論：已修好。**

- **entry 層**：不再把 BDF 換成 `<bdf>`，所以兩張卡相同訊息會是 **兩筆** entry（保留裝置位址）。
- **fingerprint 層**：簽章會把 BDF 正規化掉，避免每次開機 BDF 重編號就讓既有 bundle 被誤判 NEW。
- 測試：`test_bundle_keeps_distinct_device_addresses`、`test_bundle_fingerprint_ignores_device_addresses`。

白話：同一張卡重複印 → 併成一筆計數；不同卡印一樣的話 → 各自一筆、都看得到。簽章不含位址，所以不會亂標 NEW。

### D. dmesg fallback parser 是否把真正 nvme / mlx5 錯誤當 BENIGN 漏掉？

**結論：已修好。**

- `BUNDLE_BENIGN` 已移除 `nvme\S*` / `mlx5\S*` / `NVRM:` / `EDAC` 這種「裸 token」當續行的規則（那些不是續行標記，會把真錯誤吞掉），只留真正的 `AER:` / `PCIe Bus Error:`。
- `mlx5_cmd_check timeout` → `DMESG_BUNDLE`；`nvme nvme0: I/O ... timeout` → `DMESG_NVME`。
- 正常的 `nvme nvme0: Shutdown timeout set to 10 seconds` 仍維持 benign（由 `timeout set to` 規則保護）。
- 測試：`test_genuine_device_errors_are_not_treated_as_benign` + 既有 `test_normal_initialization_is_not_an_error`。

### E. `write_reports()` 拋例外時 `finally` 是否把 COMPLETE 誤改成 INCOMPLETE？

**結論：已修好。**

- 終態先用 `write_journal()` 單獨存 verdict，再用 `safe_write_reports()` 產 HTML（失敗只印訊息、不中斷、不改 verdict）。
- `finally` 只在 `not verdict_fixed`（即「還沒走到終態就異常 unwind」）時才標 INCOMPLETE。
- 我另外合成驗證：先把 verdict 寫成 COMPLETE，再模擬 render 拋錯 → journal 仍是 COMPLETE。

### F. Redfish EventLog / SEL 是否共用 Delta IDs、`|` 被截斷、Warning→Critical、KNOWN/NEW？

**結論：`|` 截斷與 Warning→Critical 已處理；但發現並修好一個「跨服務 id 碰撞」的真 bug。**

- **`|` 截斷**：`split('|', 2)` 已在 `_finding_html_compact` 與 `aggregate_issues` 使用，message 內含 `|` 不再被切斷（測試 `MessageWithPipeTests`）。
- **Warning→Critical**：`redfish_delta` 的 key 刻意排除 severity，所以升級會被認成「同一事件 + escalation」，不是兩筆新 issue。
- **★ 跨服務 id 碰撞（本次新修）**：原本 `eventlog_delta_ids` 把 EventLog 與 SEL 的 id 混成一個扁平集合，而 `aggregate_issues` 只取 `identity.split('|',2)[1]`（單看 id）。當某 BMC 的 EventLog 與 SEL 都有 id=5，會發生「SEL 的新事件把 EventLog 的 id=5 誤標成 NEW」。
  - 修法：新增服務限定的 `redfish_delta_ids`（鍵為 `EventLog|5` / `SEL|5`），比對時用「服務+id」；舊 journal 的扁平 `eventlog_delta_ids` 仍可讀（向後相容）。
  - 測試：`CrossServiceDeltaIdTests`（含 legacy 相容）。

### G. Hostname 嚴格度是否該改成「PRE 不符就禁止開始」？

**結論：不動現行規則（依使用者指示），僅做安全性/需求衝突分析。**

| 情境 | 現行行為 | 分析 |
|---|---|---|
| PRE hostname 不符 inventory | `HOSTNAME_MISMATCH` **WARN**、繼續跑 | 依 AGENTS.md 為軟檢查；若改硬擋，會在「inventory 寫錯但機器其實對」時誤擋整批 |
| hostname 空白（expected 或 actual） | **不檢查** | 空 expected = 不檢查，是文件化語意 |
| boot_id 格式非法 | **硬擋**（`IdentityUnsafe`） | 防止誤把別台機器/異常開機當成本次 cycle，這是必要的硬護欄 |
| 跑動期間 hostname 變更 | 每 loop 重讀 identity，會再記一次 WARN | 屬「可觀察但不致命」 |

衝突點：把 hostname 從 WARN 改成「硬擋」會與「inventory 為軟性參考、允許 placeholder」的既有需求衝突，且會讓一個打字錯誤使整個 campaign 無法啟動。**建議維持 WARN**；若真要加強，應另設「inventory 標記為 strict 的節點才硬擋」而非全體硬擋。

### H. Campaign Journal 改名 / 複製 / 損毀 的離線 recovery？

**結論：已強化，但**——我另外用真實資料抓到一個**舊格式 campaign 會讓 rebuild 崩潰**的 bug，已修（見第四節）。

| 情境 | 行為 |
|---|---|
| 資料夾複製後離線 rebuild | 支援（`journal_candidates` 依序找 override → 目錄名 → in-bundle → run_id） |
| 資料夾改名 | 從 `cycle_summary.txt` 回復 Run ID 後可找到 |
| journal 名稱/位置不同 | `--journal <path>` 明確指定 |
| journal 整份缺失 | `FileNotFoundError`，訊息列出**所有**候選路徑並提示 `--journal` |
| journal 損毀（非法 JSON） | 讀取時 `json.loads` 會拋 `ValueError`（屬明確失敗，非靜默） |
